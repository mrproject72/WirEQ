# Session updates — 2026-10-11

## Stepper frequency fix: re-space to the even grid (commit pending)

User report: after the ~15 kHz band, `+` jumped back to 194 Hz and the
graph looked non-proportional. Cause: `default_bands()` slots 10..31 use
the 32-band log spacing while the first 10 use the 10-band grid, and the
stepper took the next slot of the mixed set (grid(32)[10] = 194.1 Hz).

Fix:

- On the default grid the stepper re-spaces the WHOLE visible row to the
  even grid of the new count (`compute_log_spaced_band_defaults`),
  preserving per-band gains/types — the dots stay proportional across
  20 Hz..20 kHz and every band lands in sorted order. `−` re-spaces the
  survivors, so +/− cycles are exactly reversible.
- Off the grid (presets/AutoEq imports with their own frequencies)
  nothing is re-spaced: `+` inserts a flat Bell at the centre of the
  widest log-gap (edges included, `largest_gap_frequency`), `−` removes
  the highest-frequency band.
- `core::bands_match_log_grid` / `bands_match_log_grid_frequencies`
  (unit-tested) detect which case applies.

Server-side verified via pw-dump `Props`: 10 → + → grid(11)
(28.7 … 15336.7) → ± presses → back to the exact original grid(10)
(30.0, 59.8, … 15011.9). Native suite 47/47, gold path 10/10, 147 unit
tests, clippy/fmt clean. Flatpak rebuilt from this commit and
re-installed for the user.

## Band-count stepper + full-payload push fix (commit pending)

**Fixed a real leftover-wet-state bug** that shrinking the band count
(preset load or the new stepper) exposed: the DSP push only addressed the
visible prefix, so chain nodes dropped from the payload kept the last wet
controls they were pushed — audibly stuck filters. The tick payload now
covers ALL 32 faders on every push (upstream parity: upstream always
pushes its full band list), 332 controls; Off bands cross to dry and the
graph skips Off bands when drawing dots, so the hidden tail is both
silent and invisible. The startup push is now 332, not 112.

**The band-count stepper** (the +/− next to the "N Bands" chip in the
graph's focus row): `+` activates the next log-spaced slot as a flat
Bell, `−` deactivates the last visible band; both ride the same paths a
preset load uses (profile count, card visibility, selection clamp, chain
rebuild on type change). Sensitivity is bounded 1..=32 in the tick.
Live-verified via AT-SPI: + → "11 Bands", − → "10 Bands", each with a
full 332-control push. Native suite 47/47, gold path 10/10, 146 unit
tests, clippy/fmt clean.

## Fader row: more than 10 bands from a loaded profile (commit `c0793b7`)

The fader row was built once with `DEFAULT_ACTIVE_BANDS` (10) widgets and
preset applies synced faders by index into that fixed set — any profile
wider than 10 bands (AutoEq/APO imports reach 32) was silently truncated
in both the UI and the DSP payload.

Ported upstream's design (build-once, toggle-visibility):

- `build_band_faders` builds all 32 faders; `set_visible_band_fader_count`
  shows the prefix and adapts the scroller — NEVER up to 10 bands (the
  compact shrink-to-fit row and the 648px window minimum are untouched),
  AUTOMATIC beyond, so excess bands get a horizontal scrollbar at each
  fader's 44px minimum width instead of being crushed.
- `core::profile_band_count` / `fader_band_count_for_profile` (upstream
  ports): the profile is the prefix up to the last non-Off band, clamped
  to 1..=MAX_BANDS.
- `visible_band_count` Cell in window.rs feeds every payload source: the
  DSP snapshot, the graph, the band-count chip, the signature/Save state.
  Preset apply/reset and the per-device curve restore recompute it; a
  selection beyond the new prefix is dropped.
- The 10-band default push stays byte-identical (112 controls); growth
  beyond the chain's band count rebuilds via the existing
  `bands.len() > cur.len()` guard.

Live-verified: 20-band preset → chain rebuilt to 20 bq_peaking nodes +
212-control pushes + "20 Bands" chip (read via AT-SPI); Neutral → back
to 10 faders + 112 controls. Native suite 47/47, gold path 10/10,
146 unit tests, clippy/fmt clean.

## Backend test coverage, part 2 (commit `92091c9`)

Continued from the previous session's uncommitted WIP. TODO.md item 4 is
now DONE: `pipewire_backend.rs`'s live-control wire format is pinned by
unit tests (144 total, up from 141).

### What was already in the tree

The previous session left uncommitted tests in `filter_chain.rs` and a
test-only `parse_props_controls_pod` helper in `pipewire_backend.rs`.
They had never been compiled or run and had three bugs:

1. **`PodProp: Copy`** — `obj.props().next().copied()` doesn't compile;
   `PodProp` is not `Copy`. `props()` yields by value, so just
   `.next()?`.
2. **String parsing** — `name.as_bytes()` on a pod returns the whole pod
   *including the 8-byte header* (`[size:u32][type:u32]body`), so the
   parsed names were garbage like `\u{c}\0\0\0\u{8}\0\0\0preamp_l:b0`.
   Fixed by using `get_string_raw()` → `Option<&CStr>`.
3. **Wrong band count** — the tests called
   `native_biquad_control_values(&default_bands(), …)`, but
   `default_bands()` returns all 32 slots (332 controls), while runtime
   pushes only the active fader snapshot (10 bands → 112 controls,
   matching the "pushed 112 control(s)" log line). Tests now slice
   `&default_bands()[..DEFAULT_ACTIVE_BANDS]`.

### The round-trip contract

The wire carries **f32** (upstream casts `(float) value` before building
the pod), so the round-trip assertion is exact `f32` equality, not a
1e-6 f64 tolerance — a f64-frequency like 119.24354052777788 legitimately
round-trips as 119.24353790283203.

### What the new tests pin

- `wire_bytes_round_trip_the_control_values`: build → parse → compare
  every (name, value); guards the Double-vs-Float class of regression
  that killed the flatpak push.
- `native_control_set_covers_the_full_push`: exactly 112 controls at 10
  active bands — preamp `b0..a2` both sides + per-band `Freq`/`Q`/`Gain`
  and mixer `Gain 1`/`Gain 2` both sides.
- `bypass_push_is_all_neutral`: bypass crosses every mixer dry
  (Gain 1 = 0, Gain 2 = 1) while the filters stay addressed, so a
  re-enable restores the curve without re-pushing the filters.
